# RF20 — API de aplicación para datasets, runs cloud y drilldown seguro

## Alcance implementado

Este bloque deja operativa la capa de aplicación completa para RF20 base:

- subida y registro de datasets ERP controlados en ZIP
- listado y detalle de datasets disponibles
- lanzamiento de runs cloud en `pipeline_mode=graph`
- soporte de `scope=p2p|o2c|both`
- consulta de estado de runs
- lectura de artefactos `graph/*` en formato preparado para UI
- drilldown seguro sin SQL libre
- interfaz `Streamlit` multipágina conectada a la API

No se introduce ninguna modificación en el motor analítico que rompa:

- ECS/Fargate
- persistencia en S3
- `graph` para `p2p`
- `graph` para `o2c`
- runs sin rebuild KB
- runs con rebuild KB explícito

## Decisiones funcionales cerradas

### `scope=both`

`both` no es un `process_family` nuevo.

La API lo implementa como orquestación de dos runs separados:

- un run `p2p`
- un run `o2c`

La respuesta de creación devuelve `composite_run=true` y referencias separadas para ambas ejecuciones.

### KB y rebuild

La API expone `kb_index_enabled` como flag de petición al lanzar un run cloud.

La semántica operativa existente se mantiene:

- la KB se usa por defecto en el análisis
- `kb_index` solo reconstruye cuando se pasa explícitamente `--kb-index-enabled`
- sin rebuild: `kb_index_status=SKIPPED_NO_REBUILD`
- con rebuild: `kb_index_status=OK`

### Drilldown

El drilldown de la API no acepta SQL arbitrario.

Se implementa con:

- allowlist de acciones
- payload validado con Pydantic
- reutilización del motor seguro ya existente en `src/erp_fraud/catalog/drilldown.py`

## Estructura backend

Se introduce una separación explícita entre routers, schemas y services:

- `app/api/main.py`
- `app/api/routers/`
- `app/api/schemas/`
- `app/api/services/`

Servicios principales:

- `datasets_service.py`: validación y registro de ZIPs controlados
- `runs_service.py`: orquestación de runs cloud y lectura de estado
- `results_service.py`: shaping de artefactos `graph/*` para UI
- `drilldown_service.py`: ejecución de drilldown seguro
- `aws_service.py`: acceso a S3/ECS con la configuración cloud validada

## Modelado de datos

Schemas principales definidos:

- datasets
- runs
- report/resultados
- drilldown
- errores

`POST /runs` acepta al menos:

- `dataset_id`
- `scope`
- `pipeline_mode`
- `llm_mode`
- `kb_index_enabled`

Restricciones funcionales:

- `pipeline_mode` queda fijado a `graph`
- `scope` admite `p2p`, `o2c` y `both`
- `both` se expone como run compuesto

## Resultados preparados para UI

`GET /runs/{run_id}/graph` devuelve un objeto listo para interfaz, no solo blobs crudos.

Campos clave:

- `run_id`
- `scope`
- `status`
- `graph_status`
- `kb_index_status`
- `counts`
- `hypotheses`
- `selected_tests`
- `findings`
- `scores`
- `explanations`
- `second_level_analysis`

Reglas de presentación:

- `explanations`: explicación del fraude
- `second_level_analysis`: recomendaciones y siguiente paso
- `hypotheses`, `selected_tests`, `findings` y `scores`: estructura legible para UI

En la UI:

- `hypotheses` se presentan como tarjetas narrativas
- `selected_tests` como tabla legible
- `findings` como lista enriquecida con acceso a detalle
- `scores` como resumen tabular
- `explanations` como bloque de explicación del fraude detectado
- `second_level_analysis` como recomendaciones y siguientes pasos

## Datasets

La subida de datasets usa validación básica sobre ZIP controlado:

- nombre esperado `.zip`
- lectura segura del contenido
- validación sobre el formato `joint_datasets/`
- persistencia en S3 por scope
- registro de metadatos en un registry dedicado

Para `scope=both`, la API registra el dataset en ambos ámbitos soportados.

## Estado y resultados de runs

La API consulta estado a partir de:

- `api_request.json`
- `run_metadata.json`
- `graph/graph_state.json`
- estado ECS cuando todavía no hay estado final persistido

Esto permite distinguir de forma estable:

- `SUBMITTED`
- `RUNNING`
- `COMPLETED`
- `FAILED`

## Drilldown seguro

Acciones permitidas en esta base RF20:

- `finding_rows`

El payload valida:

- `action`
- `test_id`
- `keys`
- `extra_filters`
- `limit_rows`
- `order_direction`

El servicio reconstruye un DuckDB temporal/cacheado a partir del dataset del run y ejecuta el drilldown seguro del catálogo.

## Ejecución de la interfaz

Con la API disponible en `http://localhost:8000/api/v1`:

```bash
streamlit run app/ui/Home.py
```

Opcionalmente puede configurarse otra base URL:

```bash
export ERP_FRAUD_API_BASE_URL="http://localhost:8000/api/v1"
streamlit run app/ui/Home.py
```
